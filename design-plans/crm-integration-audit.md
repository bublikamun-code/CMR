Дата: 17.09.2026. Базовый commit: `9afab6ea0a08689a6635293a2bd163b52af5f1e4`; анализ включает незакоммиченный интерфейс.

## Вывод и границы

**Новый интерфейс пока нельзя выпускать вместо рабочей CRM.** Навигация и сценарии карточки реализованы в локальном предпросмотре, но данные канбана генерируются в памяти, а финансы содержат отдельные примеры. Перезагрузка сбрасывает изменения. Поставщики и админка недоступны в предпросмотре; пульт, клиенты и задачи не имеют полного рабочего CRUD. Это не готовая интеграция.

В ходе этой работы не переносились, не удалялись и не мигрировались реальные записи. Бот не запускался. Рабочие БД, секреты и реальные вложения не читались. Поэтому отсутствие потери данных на сервере **не подтверждено**: это аудит исходников и тестовой схемы, а не сверка фактических записей. Перед выпуском нужна сверка на согласованной копии.

## 3. Бот: действующий поток и подтверждённые риски

Поток: Telegram → выбор магазина/фото → OCR → группировка страниц → HTTP API CRM → `nakladnye` и файлы. Прямой записи бота в SQLite в рассмотренном потоке нет. Источник: `/Users/yaroslav/cmr-svetvdome/telegram_nakladnye_bot.py:143-354`.

Используются `/nakladnye/bot/check-duplicate`, `/nakladnye/bot/create`, PATCH `/nakladnye/bot/{id}`, POST `/nakladnye/bot/{id}/photos`. Сохранить контракт и серверную авторизацию; секрет бота нельзя переносить в браузер. Новый экран входящих должен читать те же записи через CRM API `/nakladnye`, а не создавать отдельный список.

При повторе бот обновляет товары и добавляет фото. Сервер нормализует серию/номер через `/Users/yaroslav/cmr-svetvdome/models.py:432-536`; уникальность защищает индекс миграции 0005 и commit guard `/Users/yaroslav/cmr-svetvdome/services/nakladnye.py:53-93`. Предварительная проверка дубля не заменяет защиту транзакции.

**Риски, требующие отдельных исправлений и тестов до выпуска:**

1. **Ложное подтверждение сохранения.** `telegram_nakladnye_bot.py:267-282` только пишет ошибку создания в лог, а `:342-350` считает сохранёнными все результаты OCR без метки дубля, независимо от успешного ответа сервера. Результат должен учитывать подтверждённые ID и отдельно сообщать неуспех.
2. **Частичное сохранение фото/товаров.** Ответы PATCH и загрузки фото в `:251-280` не проверяются. Сохранение накладной и загрузка её фото — разные HTTP-операции, не единая транзакция. Нужны статус каждого файла, безопасное повторение и явное сообщение о неполном комплекте.
3. **Замена товаров при повторе.** Ветка дубля отправляет весь `products`, сервер `nakladnye_router.py:465-470` заменяет `products_json`. Более неполный OCR может затереть исправленные товары. Нужна политика подтверждения/версий, а не безусловная замена.
4. **Группировка только по номеру.** `telegram_nakladnye_bot.py:179-186` объединяет страницы по `doc_number`, хотя сервер различает серию и номер. Разные серии с одинаковым номером и несколько результатов без номера могут объединиться до сохранения. Нужны тесты этих случаев и безопасное разделение нераспознанных документов.
5. **Ограничение списка не равно полному архиву.** `nakladnye_router.py:88` ограничивает выборку 5000 строками, затем фильтрует даты в Python. Отсутствие старого документа в ответе нельзя трактовать как отсутствие записи в БД. Перед полной сверкой/архивом нужна корректная серверная фильтрация и пагинация.

Это подтверждённые ветви кода, не утверждение о фактически потерянных документах. В этой итерации бот не изменялся.

## 5. Безопасный порядок подключения

1. Составить список используемых пользователем функций и ролей. Сохранить старую CRM доступной до подтверждённого паритета; не перенаправлять её стартовую страницу на предпросмотр.
2. Сделать согласованную SQLite-совместимую резервную копию основной и всех tenant-БД вместе с каталогами вложений. При активном WAL нельзя полагаться на простое копирование только `.db`. Проверить восстановление в изолированное окружение без исходящих уведомлений, бота и автоматизаций. В этой работе копия не создавалась.
3. На копии зафиксировать количество строк по каждой таблице, наборы ID, связи, суммы и остатки, число/контрольные суммы вложений. Проверить `integrity_check` и `foreign_key_check`. Сверять архив включая мягко удалённые сделки, а не только активный список UI.
4. Подключить новый UI сначала только на чтение через существующий API/авторизацию. Удалить генераторы и независимые фикстуры из рабочего режима. Сверить данные по ID со старым UI, включая частичные оплаты, группы, документы и записи бота.
5. Подключать запись по разделам: карточка/справочники → закупки/вложения → оплата → выписка/группы → входящие/задачи. Сохранять серверные операции и границы транзакций. При сетевой ошибке не показывать успех и не повторять денежную операцию вслепую.
6. Отдельно согласовать новые условия оплаты и семантику закупки. Если нужны новые поля — добавочная версионированная миграция с сохранением старых значений и тестом старых записей; никаких DROP/пересоздания таблиц из демоданных.
7. Исправить риски бота из раздела 3 с тестами неуспешного создания, частичной загрузки фото, повторной отправки, неполного OCR и разных серий. Новый UI сам по себе эти риски не исправит.
8. Выпускать только после сверки с копией и пользовательской приёмки. Откат интерфейса должен возвращать старые ассеты, а не восстанавливать старую БД поверх новых операций пользователей. Восстановление данных — отдельная согласованная процедура.
