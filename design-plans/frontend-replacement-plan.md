# План замены фронтенда: shell-v2 → прод

Дата: 17.09.2026. База: коммит `c06aaba` (прототип + проверки).
Связанные документы: `design-plans/crm-integration-audit.md` (контракты и
риски), `tools/mockups/README.md` (что уже сделано в v2), `HANDOFF.md`
(прод и правила работы).

## 0. Что есть и чего добиваемся

- **Старый фронт** (боевой): `js/*.js`, `css/style.css`, vanilla без сборки,
  деплой rsync, кэш-бастеры `tools/stamp_assets.py`.
- **Прототип v2**: `tools/mockups/shell-v2-prototype.html` — все ключевые
  экраны на демо-«сервере» `shell-v2-data.js`; структура данных совпадает с
  прод-моделями (справочники, сущности с ID, группы списаний, `paid_amount`,
  копейки). Проверки — `tools/visual-check/*.mjs` (6 сценариев, все зелёные).
- **Цель**: v2 становится боевым фронтом по адресу `/`, старый UI остаётся
  доступным как `/legacy` на период приёмки. Бекенд не переписывается;
  единственная планируемая миграция данных — `payment_terms` (см. Этап 2.4).

Принципы: чтение раньше записи; запись по разделам от наименее рискованного
к деньгам; сверка данных по ID на копии боевой БД перед каждым расширением;
откат — возврат старых ассетов, никогда не «восстановление данных».

## Этап 0 — фундамент (без прод-рисков)

1. **Свести репозитории.** Сейчас два рабочих ствола: `~/Documents/crm-svetvdome`
   (аудиты/бэкапы, `tools/deploy.sh` c `.pm2.env`) и `~/cmr-svetvdome`
   (фаза UX, `scripts/deploy.sh`, GitHub-remote). Выбрать источник правды
   по фронтенду, перенести непересекающиеся исправления, зафиксировать
   один деплой-путь. Решение владельца.
2. **Каркас v2 в прод-структуре**: `site-v2/` c `index.html`/`admin.html`
   по образцу прототипа (те же модули, без папки mockups), nginx отдаёт
   `/v2/`; деплой тем же rsync; кэш-бастеры через stamp_assets и для v2.
3. **API-адаптер вместо демо-сервера**: интерфейс `KBData` сохранить
   (read-коллекции + мутации через функции), внутри — `fetch` к существующим
   эндпоинтам с флагом-источником (`DEMO` / `API`). Все экраны уже читают
   только `KBData` — интерфейсный код при переключении не меняется.
   - auth: `POST /auth/...`, хранение сессии, `apiFetch`, 401 → форма входа;
   - самостоятельный шрифт Manrope (self-host) — CSP не расширяем.
4. **Загрузка/ошибки**: скелетоны и повторные запросы — в прототипе их нет,
   потому что нет сети. Спроектировать в адаптере: retry-safe мутации,
   честный тост об ошибке, «не показывать успех при сбое».

Гейт: `/v2/` открывается с прода, показывает реальные данные в режиме
только-чтение, старый фронт не затронут, откат = удалить каталог.

## Этап 1 — чтение на реальных данных

Разделы: канбан + карточка (read), клиенты, задачи/календарь, реестр оплат
(read), поставщики. Источники контрактов — таблица в
`crm-integration-audit.md` §4 (роутер/поля/ограничения).

Сверка на согласованной копии боевой БД: суммы, остатки, частичные оплаты,
группы, мягко удалённые сделки, число вложений; `integrity_check` +
`foreign_key_check`. Чек-лист — §5–6 аудита.

Гейт: владелец неделю смотрит v2 (read-only) параллельно с работой в старом
UI; расхождений по данным нет; скриншот-матрица ширин/тем зелёная.

## Этап 2 — запись по разделам (по возрастанию риска)

| # | Раздел | Контракт | Особенности |
| --- | --- | --- | --- |
| 2.1 | Карточка: поля, этап, перемещение | `PATCH /cards/{id}`, `/kanban` | скрытые поля не очищать при PATCH;乐观-обновления с откатом |

| 2.4 | Оплата | `card_details_router` | деньги; сначала тесты на копии; заодно миграция `payment_terms` (добавочная, без DROP, тест старых записей) |

Гейт на каждый пункт: e2e-сценарий (создать → изменить → отменить → сверить
в старом UI) + приёмка владельца на копии; для денег — прогон money-тестов
бека (`pytest -m money`).

## Этап 3 — остальные разделы

- Входящие от бота: тот же контракт `/nakladnye/bot/*`, новый экран читает
  `/nakladnye`; риски бота из аудита §3 чинить отдельно, UI их не маскирует.
- Почта, уведомления, workflows, кастомные объекты, сохранённые виды:
  решение по каждому — переносить в v2 или временно оставить в `/legacy`
  (переходы из v2). Таблицы и данные не удаляются ни при каком решении.
- Производительность: доска на сотнях карточек — серверные страницы +
  точечные обновления колонок (не полный `innerHTML`-перерендер), ленивая
  подгрузка очереди.

## Этап 4 — переключение и приёмка

1. nginx: `/` → v2, старый UI → `/legacy` (2–4 недели параллельно).
2. Приёмка владельцем по чек-листу: остатки и деньги, роли, бот, почта,
   календарь/задачи, печать/экспорт.
3. Откат в любой момент: перенаправить `/` на старый фронт. Данные не
   затрагиваются заменой интерфейса.

## Оценки (календарные, при работе сессиями по вечерам)

- Этап 0: 2–4 сессии (репо + каркас + адаптер-скелет).
- Этап 1: 3–6 сессий (auth, чтение, сверка).
- Этап 2: по 1–3 сессии на пункт; деньги и группы — самые дорогие.
- Этап 3–4: зависит от решений «переносить/legacy», ориентировочно 4–8 сессий.

## Риски

- **Два репозитория и два деплой-пути** — риск №1, закрыть в Этапе 0.
- Миграция `payment_terms` — только добавочная, с бэкапом `sqlite3 .backup`
  и `foreign_key_check` (правила HANDOFF).
- Копейки (v2) ↔ Numeric/FLOAT (бэк) — конвертация в одном месте адаптера,
  money-тесты.
- Safari/Firefox и реальный масштаб 75% — проверить на Этапе 1 (сейчас
  проверен только Chrome).
- Печатные формы и экспорт CSV — в прототипе отсутствуют; спланировать
  в Этапе 3, не выпускать без них.
