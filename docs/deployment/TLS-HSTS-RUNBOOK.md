# Переход CRM на доверенный TLS и HSTS

Runbook предназначен для владельца инфраструктуры. Он не заменяет отдельное
окно работ на production и не авторизует копирование репозиторных примеров
nginx на реальный сервер.

## Целевое состояние

- публичный DNS A/AAAA указывает на фактический edge nginx;
- сертификат выдан доверенным CA для точного имени сервиса;
- цепочка сертификатов проверяется обычным TLS-клиентом **без** `-k`;
- HTTP перенаправляет на HTTPS с кодом 301;
- HTTPS обслуживает CRM и возвращает `Strict-Transport-Security`;
- `CRM_COOKIE_SECURE=true` задаётся только после подтверждённого HTTPS;
- tenant-БД не считаются проверенными основным readiness и получают 503 в
  `/health/ready` до завершения собственной процедуры миграций.

## 1. Зафиксировать текущую топологию

На production нужно отдельно записать, не раскрывая содержимое env и сертификатов:

1. фактический `server_name` и все DNS-имена, которыми пользуются пользователи;
2. active nginx config (`nginx -T` в закрытом журнале работ);
3. кто terminates TLS: edge nginx, балансировщик или оба уровня;
4. адреса upstream и реальные proxy headers;
5. текущие redirect, TLS и HSTS заголовки;
6. срок действия сертификата и способ renewal.

Файлы `nginx/https.conf` и `nginx/snippets/*` — примеры. Их соответствие
production нельзя считать доказанным без чтения active host config.

## 2. DNS и firewall

До выпуска сертификата:

- добавить A/AAAA записи домена на публичный IP edge;
- удалить конфликтующие wildcard/IP записи;
- открыть TCP 80 для ACME challenge и проверки redirect;
- открыть TCP 443 для клиентов;
- backend/database не публиковать наружу без отдельной необходимости;
- проверить DNS с нескольких внешних резолверов и убедиться, что ответ ожидаемый.

Если IPv6 ещё не обслуживается корректно, AAAA-запись временно не публикуется.
Ошибочный IPv6 endpoint опаснее его отсутствия.

## 3. Доверенный сертификат

Репозиторный `scripts/setup_ssl.sh --self-signed` предназначен только для локальной
проверки. Для production используется ACME/Let's Encrypt либо выданный
внутренним CA сертификат, которому доверяют реальные клиенты.

Порядок для ACME:

1. временно оставить HTTP доступным для `/.well-known/acme-challenge/`;
2. запросить сертификат для точного `server_name` (и только нужных дополнительных
   имён);
3. разместить full chain и private key в закрытом каталоге, private key — с
   минимальными правами и владельцем nginx;
4. проверить срок действия, SAN, issuer и цепочку;
5. проверить renewal в staging, затем production renewal;
6. только после успешной проверки перейти к redirect.

Никакие значения ключей, сертификатов или env в отчёт не копируются.

## 4. Проверка TLS до включения HSTS

С внешней машины, не с самого edge:

```bash
curl --fail --show-error --silent --verbose https://DOMAIN/health/live
openssl s_client -connect DOMAIN:443 -servername DOMAIN -verify_return_error
```

Проверки:

- TLS проходит без `-k`, без отключения проверки CA и без исключения hostname;
- цепочка заканчивается доверенным CA;
- `DOMAIN` присутствует в SAN;
- нет downgrade до самоподписанного или иного сертификата;
- `/health/live` отвечает через реальный edge;
- `/health/ready` — 200 только при готовой основной БД, схеме, migration journal
  и uploads; ответ tenant-раздела трактуется честно, без выдуманного успеха.

## 5. HTTP redirect

После успешного TLS:

- `http://DOMAIN/health/live` должен вернуть 301 на HTTPS;
- исходный path и query сохраняются;
- `Location` использует заранее зафиксированное canonical HTTPS-имя, а не
  произвольное доверие к Host;
- ACME challenge продолжает обслуживаться без redirect;
- внутренний `/_nginx_live` не используется как внешний acceptance probe.

До включения redirect полезно сначала открыть HTTPS в отдельном server block
на реальном имени и проверить его обычными браузером и curl.

## 6. HSTS

HSTS включается только после устойчивого HTTPS:

1. минимум один успешный renewal-цикл;
2. подтверждены все имена, которыми открывают CRM;
3. для первого запуска рекомендуется короткий `max-age=300`;
4. после наблюдения и проверки можно переходить к `max-age=31536000`;
5. `includeSubDomains` добавляется только если все существующие и планируемые
   поддомены действительно работают по HTTPS;
6. `preload` не включается без отдельного анализа всех поддоменов, внешних
   зависимостей и последствий длительного кэширования браузерами.

HSTS не отправляется по HTTP. В репозитории это обеспечивается пустым значением
`$hsts_value` для HTTP в `nginx/snippets/hsts-map.conf`, но active production
config нужно проверить отдельно.

## 7. Cookie policy

Порядок обязателен:

1. trusted TLS и redirect подтверждены;
2. `/health/ready` возвращает 200;
3. только затем в production environment явно задаётся
   `CRM_COOKIE_SECURE=true`;
4. backend перезапускается;
5. безопасным read-only способом проверяется, что `Set-Cookie` login содержит
   `Secure`, `HttpOnly` и подходящий `SameSite`.

Нельзя сначала включать `Secure` на HTTP: браузер перестанет отправлять cookie и
вход станет невозможен. Значение нельзя выводить из `X-Forwarded-Proto` или иного
заголовка, доступного клиенту.

## 8. Проверка отката

До включения HSTS сохраняется проверенная конфигурация без заголовка.
После успешного HTTPS-развёртывания откат должен быть не только «снять HSTS»:
проверяются redirect, сертификат, renewal, cookie и доступность приложения.
Короткий HSTS позволяет браузерам быстрее вернуться к HTTPS после проверки
ошибки, но не отменяет необходимость исправить сертификат.

## Acceptance чек-лист

- [ ] DNS A/AAAA совпадает с реальным edge.
- [ ] Обычная TLS-проверка проходит без `-k`.
- [ ] Certificate SAN и цепочка корректны.
- [ ] HTTP 301 сохраняет path/query и ведёт на canonical HTTPS.
- [ ] HTTPS `/health/live` возвращает 200.
- [ ] HTTPS `/health/ready` проверен; tenant-ограничения не скрыты.
- [ ] HSTS присутствует только на HTTPS.
- [ ] `includeSubDomains` проверен; `preload` не добавлен без отдельного решения.
- [ ] Renewal проверен в staging и production-расписании.
- [ ] `CRM_COOKIE_SECURE=true` задан только после подтверждённого HTTPS.
- [ ] Login cookie имеет `Secure`, `HttpOnly`, `SameSite=Lax` и `Path=/`.
- [ ] Redirect, TLS и cookies проверены с внешней машины и в реальном браузере.
- [ ] Активная production-конфигурация записана отдельно от repository examples.

## Что остаётся отдельным owner-controlled действием

- покупка/настройка имени;
- изменение DNS;
- выпуск и хранение сертификата;
- редактирование active host nginx;
- firewall и публикация портов;
- backup;
- `CRM_COOKIE_SECURE=true` в реальном production env;
- перезапуск PM2/nginx;
- включение HSTS после доказательства стабильного HTTPS.
