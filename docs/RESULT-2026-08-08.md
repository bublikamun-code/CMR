## Баг из боевых логов: 500 у всех арендаторов на запись

В `crm-error.log` на сервере — 2556 `ResponseValidationError`. Причина найдена и
воспроизведена локально.

### Что происходило

Роутеры открывают сессию арендатора через `_db(current_user, db)` и закрывают её
сами в `finally:`. Этот блок выполняется **до** того, как FastAPI сериализует
ответ. Pydantic обращается к связям (`Card.owner`, `.client`, `.tags`,
`.attachments`, `.checklists`) уже на отсоединённом объекте — запрос падает с 500,
хотя запись в базу прошла успешно.

У superadmin этого не было: его сессия приходит из `get_db()` — yield-зависимости,
которую FastAPI закрывает **после** сериализации.

```
POST  /kanban/cards            от арендатора -> 500   от superadmin -> 200
PATCH /kanban/cards/{id}/status от арендатора -> 500   от superadmin -> 200
PATCH /cards/{id}               от арендатора -> 500   от superadmin -> 200
```

### Почему это не заметили раньше

В `clients_router` уже стоял точечный фикс с комментарием — повторный
`tdb.refresh()` после второго commit. Он работает только потому, что у
`ClientResponse` нет вложенных связей. Проверено: `refresh()` восстанавливает лишь
скалярные колонки, relationship-ы остаются незагруженными.

```
после refresh + close():  title OK, status OK
                          owner / client / tags / attachments -> DetachedInstanceError
```

### Как исправлено

Вместо правки 51 обработчика — отложенное закрытие в `database.py`: первый
`close()` сессии арендатора регистрируется и выполняется в конце запроса, вместе
с `get_db()`. Вне запроса (фоновые задачи, CLI) поведение не меняется.

| # | Проблема | Проявление | Что сделано |
|---|----------|-----------|-------------|
| 26 | Сессия арендатора закрывалась до сериализации | 500 на всех операциях записи у арендаторов | Отложенное закрытие через `defer_close` |
| 27 | `ContextVar.reset()` в sync-зависимости | `ValueError: Token was created in a different Context` | Список захватывается напрямую, токен не сбрасывается |
| 28 | `get_db` была sync-зависимостью | FastAPI выполняет их в threadpool с **копией** контекста — отложенные закрытия молча терялись | `get_db` объявлена `async`; создание сессии не делает I/O и не блокирует loop |

Проверено после исправления: три эндпоинта отдают 200 с полными связями,
`active_sessions` возвращается к 0 после 40 запросов, изоляция арендаторов цела
(199 карточек у superadmin против 5 у арендатора — разные файлы БД).

## Инцидент при очистке тестовых данных

При удалении тестовых записей я применил `LIKE '__%'`. В SQLite `_` в `LIKE` —
подстановочный символ на один любой знак, поэтому шаблон совпал со **всеми**
записями: из общей базы удалились 497 карточек, 14 клиентов и 19 поставщиков.

Восстановлено полностью из бэкапа, снятого часом ранее тем самым
`scripts/backup_db.sh`:

```
бэкап 23:29 -> integrity ok, 497 карточек
после восстановления: 497 карточек, 14 клиентов, 19 поставщиков, 6 пользователей
```

Данные арендатора 3 не пострадали — та база была создана пустой при первом входе
тестового пользователя и содержала только тестовые записи.

Выводы:

- в SQL-условиях по именам использовать `==`, а не `LIKE`, если в строке есть `_`;
- бэкап оправдал себя в первый же день: без `.backup`-скрипта данные были бы
  потеряны, а рекомендованный ранее в документации `cp` дал бы непригодную копию.

После правки: `POST /email-parser/sync` → **200**,
`{"success": true, "count": 0}`. Ошибок расшифровки в логах нет — почтовый ключ
шифрования перенесён в том отдельно, сохранённый пароль читается.

Отдельный вопрос к владельцу: у всех 497 карточек `tenant_id = NULL` —
многотенантность фактически не используется, все работают в общей базе.

## Два предупреждения

**Патч из Phase 2 применять нельзя.** Предложенная там проверка

```python
if card.tenant_id != current_user.tenant_id: raise HTTPException(403)
```

при `tenant_id = NULL` у всех 497 карточек даст 403 на каждой и положит CRM.

**Чистить git от `.secret_key` не нужно.** `git log --all -- '*.secret_key'`
показывает 0 коммитов: файла там никогда не было. Реальная утечка была в
другом — ключ уезжал в Docker-образ, и она закрыта (пункт 4).
