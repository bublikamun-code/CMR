Полный аудит боевого сервера (87.232.64.12) и нового фронтенда site-v2 на
предмет совместимости, работоспособности всех бизнес-систем и юзабилити.
**Ничего не исправлялось** — только проверки и фиксация фактов. Все

## Часть 1. Полный аудит (прод + код + реплика)

### Методика — четыре угла одновременно

1. **Пять субагентов** (параллельно):
   - сверка всех сетевых вызовов v2 с FastAPI-роутерами (53 уникальные пары
     метод+endpoint, 77 точек вызова);
   - бизнес-инварианты бэкенда по коду (12 разделов);
   - целостность сборки site-v2: свежесть, CSP, обработчики, XSS, дубли;
   - локальные гейты (`check_js`, `scripts/check.sh`, штампы, py_compile);
   - прод-инфраструктура по SSH (PM2, cron, миграции, SQLite, nginx, бэкапы).
2. **Живой обход прода браузером** (временный `audit_tmp`, только чтение):
   вход, доска, карточки, финансы, документы, клиенты, поставщики, админка,
   корзина, очереди, тёмная тема, старый фронт.
3. **Мутационная матрица** — на локальной реплике с консистентной копией
   прод-БД (VACUUM INTO): создание сделки, закупка, все 6 режимов оплаты,
   выписка ТН, галочки, удаление/корзина/удаление навсегда.
4. **Инфраструктура**: PM2, watchdog, миграции, SQLite-целостность, nginx,
   бэкапы, ресурсы.

### Критичное (блокирует релиз)

**P0-1. «Накладная на группу» всегда падает 404.**
Фронт: `site-v2/js/v2/boot.js:443-444` шлёт `POST /writeoff-groups` и
`POST /writeoff-groups/{id}/issue-invoice`. Бэкенд:
`routers/writeoff_groups_router.py:15` — префикс `/writeoffs/groups`
(маршруты на `:39` и `:160`). Подтверждено вживую на проде: 404; бэкенд-путь
живой (400 на пустой запрос). Проявление: менеджер выбирает карточки в «На
списание» → «Накладная на группу» → тост «Не сохранено в CRM: Not Found»,
группа и документ не создаются нигде. Одиночная выписка ТН при этом работает.

**P0-2. Создание/правка пользователей в v2-админке молча не работает.**
Фронт: `site-v2/js/shell-v2-management.js:42` шлёт мутацию `user-save`;
обработчика в `boot.js:396-476` нет (есть мёртвый `user-create` на `:415`,
никем не вызываемый) — запрос вообще не уходит, `mutate` возвращает `false`.
Дополнительно: POST /auth/users требует пароль ≥8 символов даже для правки
(взять его неоткуда), а `full_name` отсутствует и в схеме, и в модели.
Проявление: админ заполняет форму, видит строку, после F5 записи нет — без
единого сообщения об ошибке. Прямой API создания при этом работает.

### Серьёзные (не блокируют, но заметны пользователям)

- **Свежевыпущенная ТН нельзя изменить/отменить до F5** (P1). Ответ
  issue-invoice не содержит `id` (`services/payments.py:391-403` отдаёт
  `invoice_id`), фронт ждёт `saved.id` (`board.js:1170-1172`) → у документа в
  памяти нет `txId`; «Изменить/Отменить/Списано со склада» отрабатывают
  «в пустоту» без ошибки. Подтверждено вживую: `txId = ОТСУТСТВУЕТ` до
  перезагрузки. После F5 идентификаторы появляются.
- **Кнопка «Синхронизировать сейчас» всегда показывает «не прошла»** (P1).
  Фронт (`management.js:181-186`) читает `res.results[0]`/`res.total_count`;
  бэкенд (`email_parser_router.py:536-557`) возвращает `{success, count, cards}`.
  Письма при этом импортируются.
- **«Закрыто из баланса» не проверяет баланс** (P1).
  `card_details_router.py:496-497` — ветка `from_balance` пишется в журнал,
  баланс не запрашивается: карточка закроется даже при нехватке денег, баланс
  молча уйдёт в минус. Журнал «Закрыто из баланса» не пишется вовсе (append
  после `_log_card_changes`).
- **После «удалить навсегда» транзакции остаются в реестре** (P1). FK
  `ondelete="SET NULL"` (`models.py:198`), реестр показывает сирот
  (`payments_router.py:190-193`). Подтверждено: документы/записи удалённой
  карточки остаются. Группа списания при этом не пересчитывается.
- **Правка суммы ТН** через `PATCH /payments/transactions/{id}` не
  пересчитывает запись-остаток и статус карточки, без проверки дубля номера —
  реестр может разойтись с напечатанными накладными.
- **Очередь списания бэкенда** (`writeoffs_router.py:34`) показывает
  удалённые карточки (нет фильтра `is_deleted`); `execute` закрывает карточку
  из любого статуса без складских флагов и записи в ленту.
- **«Не оплачен» не стирает дату отсрочки на сервере** (P1): фронт шлёт
  `payment_due_date: null` (`board.js:1139-1141`), бэкенд игнорирует None
  (`card_details_router.py:468-469`). После F5 дата возвращается.

### Инфраструктура

**Критично (не про код):**
- **Домена cmr-svetvdome.online не существует** — NXDOMAIN отовсюду, whois:
  «доступен для регистрации». Работа идёт через
  `http://87-232-64-12.nip.io` — по открытому HTTP с самоподписанным
  сертификатом. Для CRM с деньгами и клиентами это главный риск вообще.
- **Бэкапы отличные (AES-256 + PBKDF2, проверка целостности, nightly,
  ротация 14 поколений), но лежат на том же сервере** — офсайта нет.

**Здорово:** PM2 (crm + nakladnye-bot) online, watchdog каждые 5 минут
корректный (включая подъём после ребута), миграции 0001–0009 применены 1:1,
`integrity_check` ok, диск 27%, RAM с запасом, лог-ротация работает.

**Концерны среднего уровня:**
- Шторм ошибок email-sync 18–19.09 (1637 ошибок «путь вне каталога данных»)
  остановлен переносом `email_settings.json` в crm_data (03:25) + деплой
  02:45; фикс в коде есть (`_get_settings_path`), но стоит убедиться, что
  легаси-файл рядом с кодом не вернётся при следующем деплое.
- 13 FK-нарушений `activity_log → cards` (ссылки на жёстко удалённую
  карточку) — источник редких 500-х (5 за 18.09). Нужна разовая чистка +
  каскадная очистка лога при hard-delete.
- Конфиг nginx нечитаем из-под юзера (cagefs): `client_max_body_size`
  (нужно ≥25 МБ) и кэш-правила не верифицируемы. Фактический CSP содержит
  `script-src 'unsafe-inline'` — слабее конвенции проекта.
- `client_max_body_size` и заголовки статики — проверить на уровне панели.

### Код и сборка site-v2

- Сборка **байт-в-байт актуальна** относительно исходников (rebuild в /tmp,
  `diff -r` пуст); md5 34 ключевых файлов репо = прод.
- XSS: `esc()` применяется повсеместно, пользовательские данные в innerHTML
  экранированы; `eval/new Function/javascript:` — 0.
- Обработчики: все `data-*`-эмиссии подписаны, мёртвых кнопок нет.
- Синтаксис: все 10 файлов v2 проходят `node --check`; гейты 6/6 зелёные
  (344 теста бэка в том числе).
- Мелочи: дубль функции `contactPhone` (`insights.js:266` и `:270`), мёртвый
  `numericId` в boot.js, конфликт схем кэш-штампов (сборка кладёт один
  глобальный штамп, `stamp_assets.py` считает per-file — запуск без
  `--check` на site-v2 испортил бы index.html).
- Инлайн-скрипт `V2_ASSET_VER` в index.html:19 живёт только благодаря
  `unsafe-inline`; при ужесточении CSP к `'self'` сломается кэш-бастинг.

### Юзабилити (первый проход)

- Дровер карточки не закрывается при смене раздела — висит поверх «Финансов».
- В шапке дровера клиента навсегда «загружается…» — реальный баг:
  в `renderDrawer()` (`insights.js:302-315`) запрос баланса стоит до
  присвоения `var client` (hoisting) → условие всегда ложно. Баланс при этом
  корректно показывается на вкладке «Оплаты».
- У не-админа в списке пользователей фантомная строка «—» (API верно отдаёт
  только себя; лишняя строка — артефакт рендера).
- Роли: manager/warehouse/documents не разграничивают бизнес-операции
  (любой авторизованный может удалять платежи, выписывать накладные) —
  риск, осознанное упрощение, но зафиксировать стоит.

### Вердикт части 1

Данные, деньги и большинство потоков работают корректно и синхронно (реестр
сходится, 366 карточек на местах, касса сходится до копейки). Но переводить
v2 «в корень» до починки P0-1, P0-2 и домена с TLS нельзя — это первые
действия менеджера и админа.

## Часть 2. Добор: полный UI-прогон прототипа (site-v2)

Повторная проверка после замечания «тестировать прототип, а не старую
версию». Оба прохода целиком велись по прототипу: живой обход — `/v2/` на
проде, мутационные прогоны — на локальном сервере с тем же site-v2 (md5 с
продом совпадает байт-в-байт). Старый фронт упоминался одним абзацем —
30-секундный smoke-тест «не сломали ли то, на чём работают».

Закрыты сценарии, которые в первый проход проверялись не с экрана. Всё —
реальные клики в интерфейсе на копии прод-данных (тестовые карточки
«AUDIT…», убраны после).

### Прототип прошёл с экрана

- **Пульт дня**: воронка 341 652,54 BYN, просрочки, «требует внимания»,
  быстрые карточки — рендер на живых данных.
- **Задачи**: создание через диалог «+ Задача», отметка выполнения —
  сохраняется (PATCH доходит до БД).
- **Доска**: фильтр магазина сужает доску (181 → 52), поиск, колонки.
- **Карточка**: срок (ДД.ММ.ГГГГ → ISO в БД), заметка, клиент через
  комбобокс с поиском.
- **Закупка**: файл счёта прикрепляется (POST /checklists/{id}/invoice),
  после перезагрузки виден («📎 имя.pdf» + «✕» открепить); пункты, галочки
  Заказано/Получено, счётчик, примечания — из первого прохода.
- **Накладные**: частичная выписка (200 из 500 — карточка остаётся в очереди
  с остатком); полная выписка; **редактирование ТН** (номер меняется и
  хранится); **«Отменить» выписку** — двухшаговое подтверждение («Точно
  отменить?»), документ удаляется, остаток возвращается, карточка
  откатывается в «Сборку».
- **«Списано со склада»** — переживает перезагрузку, пишется в CRM
  (is_warehouse_writeoff персистентен).
- **Корзина**: «Восстановить» и «Удалить навсегда» кнопками из списка —
  работают (data-trash-restore / data-trash-purge).
- **Справочники**: поставщик и магазин создаются через UI-диалоги, доезжают
  до API (в отличие от пользователей — см. P0-2).
- **Профиль**: смена пароля работает — старый пароль сразу 401, новый пускает
  (инвалидация JWT по claim `pv`).
- **Реестр**: поиск фильтрует (215 → 5 строк).
- **Консоль чистая** — кроме ожидаемых 404 от известных дефектов (группа).

### Новые находки прототипа

1. **«Оригинал ТН возвращён» не сохраняется** (средняя, P2). Чекбокс живёт
   только в памяти вкладки: отметил → перезагрузил → сброшен. В бэкенде поля
   `originalsReturned` нет вообще (grep по .py — 0 совпадений). Нужна
   миграция колонки + приём в API, иначе менеджеры будут терять отметки.
2. **Групповая выписка при отказе «врёт» локально** (усугубление P0-1).
   Сервер ответил 404, тост показан — но фронт тут же пометил карточки
   выписанными и увёл в «Списано» (`issueGroup` мутирует память до ответа).
   До перезагрузки экран показывает успех, которого нет.
3. **Файл счёта после загрузки не появляется в строке до перезагрузки**
   (мелочь): загрузка проходит, но строка обновляется только после F5 —
   выглядит как «не прикрепилось».
4. **После смены пароля страница не перелогинивает, а молча теряет данные**
   (мелочь): текущий вид пустеет из-за 401 (реестр 0 строк), редиректа на
   логин нет — надо перезайти самому.

Также подтверждено с экрана: P0-1 (тост «Не сохранено в CRM: Not Found»
прямо с кнопки «Накладная на группу (2)») и проблема сирот — после
«удалить навсегда» документы карточки остаются в /payments/documents.

### Вердикт части 2

Прототип пройден с экрана по всем разделам дважды и под разными углами:
интерактив, сохраняемость после F5, роли, реакция на ошибки сервера. Ядро
(карточки, оплаты, касса клиента, закупка, документы, справочники, корзина)
работает и синхронно с БД. До релиза мешают те же четыре вещи, теперь
подтверждённые с экрана: **P0-1 404 групповой накладной**, **P0-2 user-save**,
**«Оригинал ТН» без сохранения**, **«нет id» у свежей ТН**. Плюс два
UX-хвоста (файл после загрузки, страница после смены пароля).

## Рекомендованный порядок починки

1. **P0-1**: поменять пути в boot.js на `/writeoffs/groups/...` (две строки) —
   или добавить алиас в роутер. Плюс не мутировать карточки до успешного

4. **txId в ответе issue-invoice** (вернуть `id` из сервиса) — починит
   правку/отмену свежих ТН без F5.
5. **Миграция для originalsReturned** + приём в API + PATCH-персист.
6. Мелкие UX: файл после загрузки (перерисовать строку), редирект на логин
   после смены пароля, чистка FK-сирот activity_log, «загружается…» в дровере
