# Спека пункта 16, клиентская половина — двухфазная загрузка карточек (23.09.2026)

Серверная половина в main (`d6bfd29`/`c1301c3`): `/kanban/cards` и
`/payments/transactions` без `limit`/`offset` отвечают как раньше, с ними —
`{items,total,limit,offset}` + `X-Total-Count`; пороги `PAGE_DEFAULT_SIZE=50`,
`PAGE_MAX_SIZE=200` (`db_utils.py:91-92`); сортировка прежняя и тотальная
(`position, id desc`) — страницы последовательны и не перекрываются.

## 0. Дизайн: почему двухфазная загрузка, а не infinite scroll

Разведка (23.09) показала: **никакой агрегации на сервере нет** —
X-Total-Count даёт только общее число карточек. Полный обход `KBData.cards`
делают девять групп потребителей: KPI пульса и «N из M» (insights.js:113-124,
204), «Списано и очередь» (:214-223), календарь (:610-654), «Клиент 360»
(:299-301), дебиторка «Контроль» (prototype.html:1789-1824), счётчики и суммы
колонок (board.js:415-416), `#kb-queue-count` и «Найдено: N» очереди
(:1247, :1269), «Найдено: N» списка/архива (:1389-1390), discovery магазинов и
неизвестных статусов (boot:194-215). Честный infinite scroll по колонкам
потребовал бы серверных фильтров по стадиям и агрегатов — это новый бэк,
которого пункт не предполагает, а частичный массив молча занижает все эти
числа. Поэтому:

- **фаза 1** — `/kanban/cards?limit=80&offset=0` (88.6 КБ на копии прода,
  полный ответ 496 КБ; бар критерия < 100 КБ) → сборка и первая отрисовка
  как сегодня;
- **фаза 2** — сразу после первой отрисовки дозагрузка остальных страниц
  (`offset=80,160,…` до `total`) тем же порядком; страницы дописываются в
  конец `KBData.cards` — последовательные страницы сервера сохраняют shared
  order (boot строит массив в порядке ответа, moveCard сплитом его меняет —
  как и сегодня);
- триггер фазы 2 — двойной: автозапуск после первой отрисовки И кик из
  скролл-обработчиков доски/очереди/списка (для медленной сети; кик
  идемпотентен). Это и есть «дозагрузка по скроллу» критерия — проверяется
  сетевым логом (запросы `offset>0` уходят после первого скролла/отрисовки)
  и наполнением колонок;
- по завершении фазы 2 — один `kb:reloaded` (существующие слушатели доски и
  пульса перерисуются); во время загрузки счётчики честно показывают
  частичные значения, без маркеров (догрузка на ширм-линке — секунды);
- **гонки**: лоадер захватывает номер поколения данных (см. §1) и перед
  каждой дозаписью страницы сверяет его; при несовпадении (случился reload —
  applyInPlace пересобрал массив) лоадер тихо завершается — новый цикл
  запустит свежий reload.

Объём сознательно ограничен карточками. `/payments/transactions` (132 КБ)
остаётся полным: grouped-режим не имеет честной SQL-пагинации (группы
собираются из до 5000 строк, `payments_router.py:207-208, 282-294`), деньги
реестра сервер несёт сам, фин-раздел строится лениво один раз; урезание —
отдельная backend-задача (следующая за пунктом), не клиентская.

## 1. Правки

Держатель один. Файлы: `server_snapshot/tools/v2-boot-template.js`,
`server_snapshot/tools/mockups/shell-v2-board.js` (только кик из скролла),
при необходимости `server_snapshot/tools/mockups/shell-v2-insights.js` —
НЕ трогать без необходимости (перерисовка идёт через существующий
`kb:reloaded`). Стиль boot — современный, mockups — ES5; комментарии и тексты
UI по-русски; CSP без инлайн-обработчиков.

### A. `tools/v2-boot-template.js`
1. `_loadAndApplyData` (`:474-539`): ручка карточек уходит с
   `'/kanban/cards'` на `'/kanban/cards?limit=80&offset=0'`; нормализация
   ответа: страничная форма `{items,…}` → `payload.cards = items`, `total`
   сохранить (`KBData.cardsTotal = total`, `KBData.cardsLoaded =
   items.length`, `KBData.cardsComplete = loaded >= total`). Плоская форма
   (старый сервер) — как раньше, `cardsComplete = true`.
2. Счётчик поколения данных: `let dataGen = 0` на модуль; инкремент в начале
   `_loadAndApplyData`; после применения — `KBData.dataGen = dataGen`.
3. `loadRemainingCards()` — новая функция: если `cardsComplete` или уже
   идёт (`cardsLoading`) — выйти; цикл `while (loaded < total)`:
   `V2Api.api('/kanban/cards?limit=80&offset=' + loaded)` → маппинг батча
   карточек (переиспользовать сборку: вынести маппинг карточек из
   `buildKbData` в функцию, принимающую cardsRaw и зависimости — clientById,
   userById, stageOf, statuses, stores, issuedByCard, docsByCard; buildKbData
   её вызывает), ПЕРЕД дописыванием сверить `KBData.dataGen` с захваченным —
   при несовпадении выйти; append в `KBData.cards`; обновить
   `cardsLoaded/Complete`; после цикла — `document.dispatchEvent(new
   Event('kb:reloaded'))` (один раз) и `cardsLoading = false`.
   Вынести маппинг аккуратно: зависимости вычисляются в buildKbData до
   карточек; функция маппинга принимает объект-контекст.
4. Экспорт: `window.KBData.ensureCardsLoaded = loadRemainingCards`.
5. Вызов фазы 2: в конце `_loadAndApplyData` (после применения данных) —
   `setTimeout(loadRemainingCards, 0)` — после первой отрисовки. `KBData.reload`
   (`:526-533`) не менять: он зовёт `KBApi.all()` → `_loadAndApplyData`, фаза 2
   перезапустится сама.
6. Осторожно с `issuedByCard`/`docsByCard` для батчей: issued считается по
   `/payments/transactions` (загружен полностью в фазе 1) — батч-пересчёт для
   дописанных карточек обязателен (остатки, writeoff_status), иначе очередь
   «На списание» покажет «—» до следующего reload. Использовать тот же код
   пересчёта, что в buildKbData (вынести, не дублировать).

### B. `tools/mockups/shell-v2-board.js`
Кик лоадера из существующих скролл-путей (только если флаги есть — на

## 2. Критерии готовности (стенд 8127, копия прод-БД + 0013)

1. Сетевой лог boot: первый запрос `/kanban/cards?limit=80&offset=0`
   (~88 КБ < 100 КБ), затем `offset=80,160,240,320` — суммарно все 391
   активная карточка; `KBData.cards.length` = 391, уникальность id (нет
   дублей при перезагрузках и мутациях).
2. Доска после загрузки идентична прежней: те же 4 колонки с теми же
   счётчиками и суммами (13/168/4/12 на копии), очередь «На списание» 2,
   «Списано» 192; список «Найдено: 391», архив 177 — совпадение с
   pre-paging значениями.
3. Дозагрузка по скроллу: при заблокированном автозапуске (или сразу после
   boot — до завершения фазы 2) скролл колонки приводит к новым запросам
   `offset>0` (сетевой лог) и наполнению колонки.
4. Мутация во время фазы 2 не теряет и не дублирует карточки: создать сделку
   сразу после boot → после успокоения `KBData.cards` содержит её один раз,
   total-каунтеры сходятся.
5. `KBData.reload()` после мутации показывает те же финальные составы.
6. census: 0 pageerror, 0 аномалий, планка известных артефактов.
7. Перф-эталон пункта 2 не ухужшился (s11: мутации 4, PATCH 1, fin 0).
8. `node --check` на правленых файлах; пересборка одна; `scripts/check.sh`
   exit 0 (pytest 878 — бэк не тронут).
9. Предпросмотр мокапа (`file://, ?demo=1`) не сломан: `KBData.ensureCardsLoaded`
   отсутствует/безвреден, демо-карточки как были.
