# P0 хотфикс: отмена групповой ТН (спецификация, 23.09)

Статус: решение владельца 23.09 — клиентскую часть (A) выполняет сессия
пункта 3 как держатель `shell-v2-board.js`; серверную часть (B) и клиентский
переключатель (C) — воркер главной сессии после освобождения
`routers/`/`services/` (пункт 17). Реестр дефектов: `V2-WORKPLAN-2026-09-22.md`,
раздел «Дефекты доски, найденные пунктом 6», пункты 1 и 2.

## Дефект (P0, живой на проде)

`issueGroup` пишет в локальный кэш группы `serverTxId = g.id`
(`tools/mockups/shell-v2-board.js:2244`), а ветка отмены группы
(`:1806-1843`) шлёт `apiMutate('annul-tx', { txId: group.serverTxId })` →
`DELETE /payments/transactions/{group_id}` — удаляется ПОСТОРОННЯЯ
транзакция, чей числовой id совпал с id группы. После перезагрузки страницы
boot подставляет настоящий id документа (`v2-boot-template.js:339`), поэтому
бьёт только отмена в сессии выписки. До деплоя хотфикса — организационный
запрет нажимать «Отменить» у групповых ТН.

## A. Клиентская часть (сессия пункта 3, файл `tools/mockups/shell-v2-board.js`)

1. `:2244` — брать настоящий id транзакции из ответа, а не id группы:
   `serverTxId: (result && result.invoice_transaction_id) || null`
   (поля пока нет в ответе сервера — см. B; до его деплоя значение `null`,
   что безопасно: ветка отмены уйдёт в локальный путь, см. п.3).
2. Ветка отмены группы (`:1836-1843`): условие `if (group.serverTxId)`
   оставить как есть — с п.1 туда попадёт настоящий id документа группы,
   `annul-tx` удалит именно групповой документ, а не постороннюю запись.
3. Защита от ложной локальной отмены выписанной группы: перед
   `else { doCancelGroupLocal(); }` добавить ветку
   `if (group.writtenOff) { notify('Отмена групповой ТН доступна после обновления страницы.'); return; }`
   (после F5 boot даст настоящий serverTxId и отмена пройдёт серверно).
   Локальный путь оставить только для групп, реально не сохранённых
   на сервере (`writtenOff === false`).
4. Не пересобирать site-v2 отдельно: хотфикс уедет в сборку в финальной
   пересборке пункта 3 (правило одной пересборки). Деплой — решение владельца.
5. Проверки пункта 3 прогнать как обычно; дополнительно ручной сценарий на
   стенде 8126: выписать групповую ТН → «Отменить» в той же сессии →
   ожидание: уведомление из п.3, в сети НЕТ `DELETE /payments/transactions/{id}`
   с id группы; после F5 отмена проходит одним `DELETE` по настоящему id
   документа (посторонние транзакции не затронуты — сверить счётчик записей
   реестра до/после).

## B. Серверная часть (воркер главной сессии, после пункта 17)

1. `schemas.py:531 WriteoffGroupResponse` += `invoice_transaction_id: Optional[int] = None`.
2. `routers/writeoff_groups_router.py:160 issue_group_invoice`: после
   `db.commit(); db.refresh(group)` выставить `group.invoice_transaction_id = doc.id`
   (ad-hoc атрибут для from_attributes; колонку не добавлять).
3. Новый `POST /writeoffs/groups/{group_id}/annul`: удаляет групповой документ
   (`Transaction` с `writeoff_group_id=group_id`, `card_id=NULL`), снимает
   `group.written_off`, `invoice_number`, `invoice_date`, возвращает карточки
   из «Закрыто» через `writeoff_status_for` (`services/payments.py:107-127`)
   и пересчитывает остатки — зеркально семантике одиночной отмены;
   роль — по матрице пункта 17. Тесты: матрица доступа + assertions unwind
   (статусы карточек, written_off, удаление документа).
4. Миграции не нужны (ad-hoc поле ответа + существующие колонки).

## C. Клиентский переключатель (после деплоя B; держатель board.js на тот момент)

В ветке отмены группы вместо `annul-tx` вызывать `POST /writeoffs/groups/{id}/annul`;
`annul-tx` оставить фолбэком только для групп без `written_off`. Этим же
коммитом закрыть дефект 2 реестра («ложная кнопка после перезагрузки»):
локальный unwind в `doCancelGroupLocal` остаётся, но серверное состояние
теперь реально разматывается.
