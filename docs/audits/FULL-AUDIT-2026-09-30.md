## 3. 🔴 КРИТИЧНО

### К-1. Письма теряются безвозвратно и без следа
**`routers/email_parser_router.py:536` + `:737`**

Идемпотентность импорта ищется так:
```python
models.ActivityLog.details.like("%" + message_id + "%")   # :536
```
А в `details` пишется **всё письмо целиком**, включая тело:
```python
details=(f"{id_line}От: ...\nТема: {subject}\n\n{body}")[:4000]   # :737
```

**Сценарий.** Менеджер отвечает клиенту, тело ответа содержит цитату
`> Message-ID: <abc@mail.ru>`. Это письмо импортируется первым. Приходит оригинал
с тем же `Message-ID` — `_find_already_imported` находит **чужую** запись (совпадение
подстроки), `_import_email_message` возвращает `None` (`:642`), вызывающий код ставит
письму `\Seen` (`:826-828`) и идёт дальше.

**Итог:** оригинальное письмо клиента не импортировано **никогда**, без единой записи
об ошибке. В лог уходит `INFO «дубль не создаётся»`, в ответ cron — `success: true`.
Восстановление только из бэкапа БД.

Второй вектор: `_normalize_message_id` (`:495`) не проверяет минимальную длину,
поэтому короткий `a@b` матчится как подстрока в `xa@b`.

**Почему не поймали раньше:** тесты проверяют дедупликацию, но не проверяют, что
`details` содержит тело письма.

**Исправление:** отдельная колонка `message_id` + `UNIQUE (tenant_id, message_id)`.
Минимум — сравнивать только первую строку `details` (там `Message-ID: <...>`), а не
искать подстроку по всему полю, и отбрасывать ID короче 8 символов.

### К-2. Миграция 0017 может навсегда оставить пустую таблицу `webhooks`
**`migrations/0017_secure_webhook_secrets.py:110-120` + `migrate.py:88-93`**

При `isolation_level=""` модуля `sqlite3` DDL не открывает транзакцию сам. Значит
`ALTER TABLE ... RENAME` и `CREATE TABLE webhooks` коммитятся **немедленно**, а
`INSERT..SELECT` и `DROP TABLE webhooks_legacy_ba11` — уже в транзакции, которую
коммитит только `migrate.py:93`.

**Сценарий.** `migrate.py` убит (рестарт PM2, OOM, Ctrl-C) между строкой 111 и коммитом.
В БД: свежая **пустая** `webhooks` + `webhooks_legacy_ba11` со всеми данными.
Миграция не отмечена. Приложение читает `webhooks` → **все интеграции молча мертвы**.

Хуже: повторный прогон **не чинит**. `_secret_type()` вернёт `TEXT` (новая таблица
создана из `WEBHOOKS_DDL` с `secret TEXT`), поэтому ветка `_rebuild_webhooks` не
выполнится — пойдёт UPDATE по пустой таблице.

**Исправление:** явный `BEGIN IMMEDIATE` вокруг перестройки + импорт из legacy-таблицы
должен быть восстанавливающим, а не только обновляющим.

### Деньги и целостность

**Д-1. `permanent_delete_card` сносит реестр сделки вместе с аудит-трейлом**
`routers/kanban_router.py:322-338` — bulk `DELETE` всех транзакций (включая накладные
и их копии), затем `DELETE` из `record_versions` (след правок, по которому суммы
можно было бы восстановить), затем `ActivityLog`. Один коммит на `:361`. Без бэкапа,
без soft-delete, без проверки «есть ли выписанные накладные», без записи об удалении.

**Д-2. Индекс `uq_remainder_per_card` не воспроизводится ни на одной схеме `create_all`**
Индекс существует только как побочный продукт миграции `0004`; в `models.py` его нет
(`models.py:203-228`, нет `__table_args__`). На боевой БД индекс есть (`/health/ready`
требует его). Но **любая свежая установка, том Docker, восстановление из бэкапа без
`migrate.py` или любая tenant-БД** защиты не имеет → два параллельных «В Сборку»
дают **две записи-остатка по полной сумме сделки**. Репозиторий признаёт это сам в
`tests/test_payments_money.py:696-698`.
*Исправление:* добавить частичный `Index` в `Transaction.__table_args__`. **Дёшево.**

**Д-3. `update_card` пишет деньги без writer slot и без оптимистической блокировки**
`routers/card_details_router.py:569-570` (`card.total_amount = ...` безусловно),
`:597` (`db.add` нового остатка), `:687` (единственный commit). Два админа, меняющие
сумму одной сделки: последний коммит молча затирает сумму первого, и оба добавляют
свою запись-остатка → 500 или две записи. Соседний `update_card_payment` защищён
(`:751-753`) — этот нет.

**Д-4. `update_transaction_checkboxes` — нет writer slot, нет `rollback_on_error`**
`routers/payments_router.py:557-559` (каскадная правка всех записей сделки),
`:626-630` (новый остаток), `:633` (коммит). В файле ровно один `db.rollback()`,
и он в другом хендлере (`:228`). Сравните `services/payments.py:108,267,437,561`,
где `rollback_on_error` применён ко всем трём денежным сервисам.

**Д-5. `money_is_zero()` считает отрицательный остаток нулём**
`services/writeoffs.py:24` — `round(float(value or 0), 2) <= 0` вместо `== 0`.
Вместе с `+ MONEY_EPSILON` в проверках (`services/payments.py:476,636`,
`payments_router.py:607`, `card_details_router.py:786`) это даёт систематическое
**молчаливое перевыставление на 1 копейку за накладную**: остаток уходит в минус,
запись-остаток удаляется, сделка помечается «Закрыто», переизбыток нигде не отражён —
ни один отчёт его не покажет. Обнаружимо только пересчётом Σ накладных против
`card.total_amount`. На сделке с 500 накладными — до 5.00 BYN.
*Исправление:* одна строка `== 0`. **Дёшево и срочно.**

**Д-6. `repair_writeoffs` необратимо переписывает суммы по всему tenant'у**
`routers/payments_router.py:1001` перезаписывает сумму записи-остатка на
`card.total_amount − Σ issued`; исходное значение не пишется ни в `ActivityLog`,
ни в `RecordVersion`. Бэкап (`:929`) необязателен: `_backup_db_snapshot` глушит
исключение и возвращает `None` (`:73-75`), починка продолжается без страховки
(в отчёте `backup: null`). Имя файла с точностью до секунды (`:64`) — две починки
в одну секунду перезапишут бэкап друг друга.

после неудачного не получают ни доставки, ни строки в `webhook_deliveries` — нет даже
dead-letter.

**Ф-9. Суперадмин не может создать webhook или пользователя — 500 от триггера миграции 0018**

### Авторизация и изоляция tenant'ов

**А-1. Межтенантная порча данных при переименовании типа кастомного объекта**
`routers/custom_objects_router.py:257-259` выполняет
`UPDATE custom_field_defs SET relation_target=...` **без tenant-фильтра**. Миграция 0018
(`migrations/0018:233-249`) заменила глобальную уникальность имени типа на per-tenant
(`UNIQUE (tenant_id, name)`), поэтому одинаковое системное имя у разных компаний теперь
легально. `relation_target` хранит именно **имя** (`models.py:291`).
Админ tenant A вызывает `PATCH /custom/objects/{A_id} {"name":"gear"}` → `relation_target`
переписывается **у всех полей всех tenant'ов**, где стояло `equipment`. У tenant B поля-связки
молча начинают указывать на тип чужой компании. Без лога, не откатывается.

**А-2. Rate limiting покрывает 6 маршрутов из 143; бот-эндпоинты без лимита**
Единственные лимиты — `auth_router.py:21,103`, `card_details_router.py:265,374,414`,
`email_parser_router.py:910`. Без лимита остались, в частности:
`POST /nakladnye/bot/create` (`nakladnye_router.py:690`) — знание токена бота даёт
неограниченный поток записей; дорогие выгрузки `GET /kanban/export/csv`
(`kanban_router.py:377`) и `GET /nakladnye/export/products-excel`
(`nakladnye_router.py:607`) — отказ в обслуживании одним аутентифицированным аккаунтом;
`POST /payments/repair-writeoffs?dry_run=false` (`payments_router.py:886`) — массовая
перезапись реестра с гейтом только по роли.

**А-3. Админ может захватить аккаунт другого админа своего tenant'а**
`routers/auth_router.py:189-192` + `schemas.py:68-79`: `UserUpdate.password` принимается
**без старого пароля цели**, ограничение только по роли вызывающего. В `update_user` нет ни
`logger`, ни `ActivityLog` — в отличие от `change_own_password` (`:113`). Плюс `role` —
свободная строка: `{"role":"SuperAdmin"}` или `{"role":"superadmin "}` проходит проверку
`data.role in ("admin","superadmin")` (`:180`) и записывается в БД как **новая неизвестная
роль**, которая не проходит ни `require_admin`, ни `require_role` — заведомо залоченный
пользователь. Лимита на эндпоинт нет.

## 6. UX, доступность и производительность фронта

### 🔴 Производительность: 106 КБ gzip грузится на экране входа впустую

5 безусловных `<link rel="preload" as="script">` в `site-v2/index.html` для модулей
первой волны. На экране входа они **не нужны**, но браузер их качает ими. Подтверждено
на проде: 5 предупреждений `was preloaded ... but not used within a few seconds`.

| Модуль | gzip |
|---|---|
| shell-v2-board.js | 75 151 |
| shell-v2-fin.js | 24 041 |
| shell-v2-select.js | 5 116 |
| shell-v2-navigation.js | 2 200 |
| shell-v2-payment.js | 2 183 |
| **ИТОГО** | **108 691 Б (106 КБ)** |

На профиле Fast 4G это ~0.5–0.6 с канала, потраченных **до** входа — ровно там,

### С-4: почему это стоило дорого

Находка в отчёте звучала сухо — «две несовпадающие формулы». На деле человек с
реальным авансом **не мог закрыть сделку из баланса**: интерфейс показывал
«баланс: −4000 — долг клиента» и по этой же величине прятал чекбокс «закрыть
из баланса», тогда как сервер считал доступным 1000 и оплату разрешал. Деньги
в кассе были, сделку было нечем закрыть, и причина была не видна нигде.

Подтверждено на стенде функциональным аудитом: `PASS 6i. «Из баланса»: счёт
закрыт, касса не двигается — {'paid': 1000, 'status': 'Оплачен', 'cash': 3600,
'balance': 2600}`.

### С-8: находка НЕ подтвердилась, правок в коде нет

«События от суперадмина не уходят в webhook'и (фильтр `tenant_id == None`)» на
текущей схеме не воспроизводится:

* `User.tenant_id` — **NOT NULL**: суперадмин это роль, а не пользователь без
  компании;
* `Webhook.tenant_id` — **NOT NULL**: условие «`tenant_id IS NULL`» не истинно
  ни для одной строки, ветка недостижима;
* `get_current_user` отклоняет токен, у которого `tenant_id` не
  `isinstance(tenant_id, int)` — `NULL` не проходит.

Честный вывод: ветка написана про несуществующее состояние. Ни одной строки
кода ради неё не добавлено. Взамен появились 6 тестов, фиксирующих инвариант:
если схема когда-нибудь допустит пользователя без tenant'а, они провалятся —
и это будет правильный сигнал.

### С-9: почему подпись осталась по телу

Формат «`timestamp.body`» (Stripe, GitHub) надёжнее — повтор невозможен даже
внутри окна. Но он **необратимо ломает всех нынешних получателей**: их
проверка перестанет сходиться с первого обновления, а интеграции живут на
проде у клиентов. Молчаливого сбоя тут быть не может — подпись просто
перестанет проверяться, и человек узнает об этом из своего лога.

Поэтому сейчас сделано безопасно: тело подписано как было, рядом добавлен
`X-Webhook-Timestamp`. Метку нельзя подделать — она лежит и в заголовке, и
внутри подписанного тела. Переход к подписи со временем — отдельная задача
вместе с предупреждением клиентам.

### Что осталось нетронутым и почему

* **Ф-3, Ф-5** (`sync_all_tenants` не обходит все компании; `sync-overdue`
  не вызывается) — кандидат на подключение к `scripts/watchdog_crm.sh`,

* **Д-6** `repair_writeoffs` — перезаписывает суммы с неразборчивым бэкапом.

* **С-14** — внутренний токен API совпадает с токеном Telegram-бота.
  Правка ломает контракт с LLM-контуром, то есть выходит за рамки аудита.
* **С-13** — в production `CRM_CORS_ORIGINS` задан узко; дефекта нет.
* **С-15, С-17, С-18** — требуют изменений в схеме сессий и в проверке
  накладных; оценены, но не начаты.

### На заметку владельцу перед развёртыванием

1. `python3 migrate.py apply` **обязателен** — без него `PATCH /cards/{id}`
   падает в 500 (`activity_log has no column named email_message_id`,
   миграция 0019).
2. При смене домена добавить его в `CRM_CORS_ORIGINS`: список
   `TrustedHostMiddleware` выводится оттуда, и забытый домен даст 400 на все
   запросы сразу.
3. Правка подписи вебхука намеренно **не** ломает формат — переход на
   `timestamp.body` отложен осознанно, см. раздел про С-9.

### Уточнение по К-1 при реализации

Описание дефекта в разделе 3 подтвердилось, но при разборе вскрылось важное:
для срабатывания нужен **короткий ответ**. `clean_email_body` срезает цитату по
маркеру «От:»/«On … wrote:», **но только если маркер стоит дальше 40-го
символа** (`email_cleaner.py:54`) — иначе вырезалась бы вся переписка у
короткого ответа. Пока маркер в первых 40 символах, процитированный
`Message-ID` доживает в `details`, и `LIKE` находит его.

Второй вектор из раздела 3 — короткий `a@b`, матчащийся в `xa@b` — точной
сравнением тоже закрыт.

Регрессия проверена на полезность обоими концами: на старой `LIKE`-логике
`test_reply_quoting_original_message_id_is_still_imported` падает с
«импортировано 1» (теряется ровно оригинал заявки), на новой — проходит.

### Чего в Ф-4 сделано НЕ сделано

`CRM_SECRET_KEY` и `CRM_CRON_TOKEN` в production по-прежнему **не
обязательны** — fail-fast в `validate_startup_config` не добавлен. Это
изменение поведения запуска на живом проде: без переменных приложение просто
не поднимется. Решение о таком шаге остаётся за владельцем, и по утреннему
разбору его нужно принять осознанно. Рассинхрон источников (собственно причина
неработающего фона) при этом устранён.

### Уточнения по Ф-7 и С-11 при реализации

**Ф-7.** Молчаливых мест загрузки фото оказалось не одно, а **четыре**:
ветки «документ создан», «дубль по 409-гонке», «дубль, найденный через
`check-duplicate`» и «ничего не распознано». В отчёте назван только один
пример. Все четыре сведены в один помощник; иначе починенное место снова
потёкло бы при следующей же правке рядом.

**С-11.** Дефект на текущих вызывающих **латентный**: пары `type`/`entity_type`
идут один-к-одному, поэтому пересечения не происходит. Регрессия построена на
одинаковом `type` с разной сущностью — при разном `type` первая версия теста
проходила и на сломанном коде, то есть не проверяла ничего. Починено, потому
что условие неверно по существу, а первое же расширение (один `type` на две
сущности) стало бы молча глотать чужие уведомления.

### Чего в этой правке НЕ сделано

- **Ф-3** (`sync-all` не обходит tenant'ов) и **Ф-5** (`sync-overdue` никто не
  вызывает) не тронуты: первое латентно на однокомпанной базе, второе — решение
  о том, где живёт cron.
- **С-14** (внутренний токен API = токен бота, LLM в контуре доверия) — это
  про границу доверия, а не про строку кода; требует решения владельца.
